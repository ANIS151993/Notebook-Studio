\begin{abstract}
Tabular data preprocessing remains one of the most labor-intensive
and least reproducible stages of analytical workflows, with analysts
routinely allocating between 60\,\% and 80\,\% of project time to
data wrangling before any exploratory or predictive analysis can
begin. This paper presents \textbf{DataMentor}, a production-deployed,
serverless platform that integrates deterministic CSV preprocessing,
browser-native Python notebook execution via the Pyodide WebAssembly
runtime, domain-aware visualization across ten chart types, and a
hybrid rule-guided runtime repair subsystem operating without external
server infrastructure. An empirical evaluation conducted over
15~heterogeneous CSV datasets spanning five domain verticals and a
purpose-built repair benchmark (DRB-100) of 100~injected Python
errors across five error classes demonstrates: (i)~a mean
preprocessing-time reduction of 91.6\,\% relative to a two-analyst
manual baseline; (ii)~an overall single-pass automatic repair
resolution rate of 82\,\%, with rule-based latency of 0.8\,s and
model-assisted latency of 6.4\,s versus a manual debugging median of
18.2\,min; and (iii)~full byte-level deterministic reproducibility
across repeated executions. Comparative analysis against nine
representative prior systems across four relevant research domains
confirms that no existing tool combines deterministic preprocessing,
installationless browser-native Python execution, domain-aware
visualization, and hybrid runtime repair in a unified,
offline-capable platform.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Data preprocessing is widely recognized as the dominant time cost in
analytical workflows~\cite{krishnan2016}. A longitudinal industry
survey reported that analysts allocate, on average, 76\,\% of total
project hours to data acquisition, cleaning, and formatting before
any exploratory or predictive modeling can
begin~\cite{crowdflower2016}. For small-to-medium enterprises (SMEs)
and academic laboratories operating without dedicated
data-engineering teams, this overhead is particularly acute: cleaning
is performed ad~hoc with heterogeneous toolchains, and the resulting
artifacts are rarely reproducible between operators or
sessions~\cite{sculley2015}.

Existing tools partially address these challenges but leave important
gaps. Notebook environments such as JupyterLab offer expressive code
cells but require local Python installations and yield non-deterministic
results when cell execution order varies. Reproducibility frameworks
such as Data Version Control (DVC)~\cite{dvc2020} and
MLflow~\cite{mlflow2018} address provenance at the experiment level
but presuppose that raw data has already been cleaned. Code-repair
tools for Python operate on source files but lack the execution-state
awareness needed to diagnose errors that arise from data-schema
mismatches within an interactive notebook session.

This paper describes \textbf{DataMentor}\,---\,a platform designed
to unify these concerns in a single, zero-installation workflow.
DataMentor is deployed at \url{https://datamentor.marcbd.site} and
built on Next.js~16, React~19, TypeScript, Pyodide~0.25, Firebase,
and Chart.js. The system makes four primary contributions:

\begin{enumerate}
  \item A \textbf{deterministic preprocessing pipeline} that
        normalizes, deduplicates, and type-classifies arbitrary CSV
        inputs through a fixed rule sequence, guaranteeing identical
        outputs for identical inputs regardless of operator.
  \item A \textbf{browser-native notebook execution engine} using
        Pyodide~\cite{pyodide2021}, which loads CPython~3.11 inside a
        WebAssembly sandbox, eliminating server-side Python
        infrastructure and maintaining complete data locality.
  \item A \textbf{domain-aware visualization system} mapping 47
        recognized column-name patterns to contextually appropriate
        chart types and evidence-grounded insight language.
  \item A \textbf{hybrid runtime repair subsystem} that applies a
        priority-ordered rule index for common Python error classes
        before escalating to a local model-assisted repair module,
        operating without any external API connection.
\end{enumerate}

The remainder of this paper is organized as follows.
Section~\ref{sec:related} positions DataMentor against prior art
across four research domains. Section~\ref{sec:arch} describes the
system architecture. Section~\ref{sec:method} details the experimental
methodology and benchmark construction. Section~\ref{sec:results}
presents quantitative results. Section~\ref{sec:discussion} interprets
findings and acknowledges limitations. Section~\ref{sec:conclusion}
concludes.

\section{Related Work}
\label{sec:related}

Prior work relevant to DataMentor spans four partially overlapping
categories: \emph{notebook-assistant systems}, \emph{reproducible
analytics frameworks}, \emph{local code-repair tools}, and
\emph{browser-based analytics platforms}. Table~\ref{tab:related}
provides a feature-level comparison across these categories.

\subsection{Notebook-Assistant Systems}

JupyterAI~\cite{jupyterai2023} integrates code-completion and inline
explanation capabilities directly into JupyterLab via an external API
connection. It reduces cell-authoring effort but does not modify the
underlying dataset, requires a locally running Jupyter server, and
provides no deterministic cleaning guarantee. Neptyne~\cite{neptyne2023}
extends spreadsheet metaphors with Python cell formulas, targeting
structured manipulation rather than statistical notebook automation.
Hex~\cite{hex2023} is a cloud-hosted collaborative notebook supporting
SQL and Python; it is subscription-gated and requires a provisioned
cloud container. Code Interpreter~\cite{openai2023}, embedded in
commercial chat interfaces, accepts uploaded CSV files and produces
analysis outputs but provides no persistent workspace, no user-visible
cleaning audit, and no domain-aware chart generation.

DataMentor differs from all four in three respects: (i)~preprocessing
is deterministic, auditable step by step, and requires no external API;
(ii)~the execution environment is fully in-browser with no server
dependency; and (iii)~the notebook layout is pre-structured with
14~guided cells introducing reproducible statistical primitives before
a free-form cell is available.

\subsection{Reproducible Analytics Frameworks}

DVC~\cite{dvc2020} addresses dataset and model provenance through
Git-integrated artifact tracking. MLflow~\cite{mlflow2018} provides
experiment logging, artifact storage, and model registry.
Sacred~\cite{sacred2017} instruments Python experiments to capture
configuration snapshots and metric traces. These frameworks excel at
pipeline-level reproducibility \emph{after} data is clean but impose
substantial setup overhead and do not address the initial normalization
of raw CSV inputs.

DataMentor operates at an earlier stage: its preprocessing pipeline
is self-contained and requires no version-control infrastructure.
Reproducibility is achieved through the deterministic, ordered
application of a fixed transformation sequence, which produces
byte-identical outputs for byte-identical inputs without external
provenance tooling.

\subsection{Local Code-Repair Tools}

DeepFix~\cite{deepfix2017} applies a sequence-to-sequence model to
correct syntactic errors in student C programs, achieving approximately
27\,\% single-pass full-program repair on the IIT~Bombay dataset.
SyntaxFix~\cite{syntaxfix2021} extends rule-based pattern matching to
Python syntax errors, covering common indentation and bracket
mismatches. Refazer~\cite{refazer2016} synthesizes program
transformations from teacher-provided correction examples. These tools
operate on file-level source code and do not target the notebook
execution context where errors typically arise from data-state
dependencies\,---\,such as a \texttt{NameError} caused by a cell
executed out of sequence.

DataMentor's repair subsystem addresses this contextual gap: it has
visibility into the loaded CSV schema, the Pyodide execution state,
and the cell execution sequence, enabling repairs that are aware of
the data context, not merely the code syntax.

\subsection{Browser-Based Analytics Platforms}

Observable~\cite{observable2021} provides a JavaScript-native reactive
notebook, but does not support CPython or pandas workflows natively.
TensorFlow.js~\cite{tensorflowjs2019} enables in-browser model
inference but targets prediction, not data preparation.
Deepnote~\cite{deepnote2022} offers real-time collaborative notebooks
but requires a provisioned cloud container rather than a WebAssembly
sandbox. Google Colab~\cite{colab2019} provides free cloud-hosted
notebooks with GPU access but requires a Google account, imposes
session time limits, and routes data through cloud infrastructure
rather than retaining it on the client device.

DataMentor is distinguished by its use of Pyodide to run authentic
CPython~3.11 with pandas, NumPy, SciPy, and Matplotlib inside the
browser\,---\,producing outputs byte-compatible with standard desktop
Python\,---\,while maintaining complete data locality: the uploaded
CSV never leaves the client device.

\subsection{Layer 1 — CSV Ingestion and Normalization}

The ingestion pipeline applies seven transformations in fixed,
deterministic order:
(1)~Papa Parse tokenization with header detection;
(2)~leading/trailing whitespace removal from all cell values;
(3)~header normalization to lowercase underscore convention
  (\texttt{Blood Pressure}\,$\to$\,\texttt{blood\_pressure});
(4)~exact-duplicate row removal via a SHA-256 fingerprint of each
  row's serialized values;
(5)~null and empty-string detection with count reporting;
(6)~column type inference (Layer~2);
(7)~schema summary generation.
The order of transformations is critical: normalization precedes
deduplication to avoid false negatives caused by whitespace variation.
The pipeline is pure (no side effects), enabling byte-identical
re-execution.

\subsection{Layer 2 — Column Type Classification}

Each column's values are classified by a majority-vote heuristic into
one of four types. A column is classified as \texttt{boolean} if its
value set is a subset of $\{0,1\}$. A column is classified as
\texttt{datetime} only if values parse as valid \texttt{Date} objects
\emph{and} do not match the regular expression
\texttt{/\textasciicircum-?\textbackslash d+(\textbackslash.\textbackslash
d+)?\$/}, which prevents pure numerics (e.g., \texttt{"63"}) from
being misclassified as years. A column is classified as
\texttt{numeric} if the majority of non-null values are finite
floating-point numbers. All remaining columns are \texttt{categorical}.

\subsection{Layer 3 — Notebook Generation Engine}

The Pyodide hook loads CPython~3.11 via WebAssembly, pre-fetching
pandas~2.0, NumPy~1.26, SciPy~1.11, and Matplotlib~3.8.
Fourteen code cells are generated from the cleaned dataset's schema.
Cells~1--7 cover data loading, shape inspection, descriptive
statistics, missing-value auditing, duplicate detection, correlation
analysis, and categorical frequency analysis. Cells~8--13 produce
Matplotlib visualizations (distribution plot, pie chart, violin plot,
heatmap, pairplot, joint plot) rendered as base64-encoded PNG images
via a \texttt{BytesIO} buffer and displayed inline without any
server round-trip. Cell~14 is an empty editor for user-authored code.

\subsection{Layer 4 — Visualization and Domain Analysis}

The visualization layer provides ten universal chart types
(DistPlot, Pie, Violin, HeatMap, PairPlot, JointPlot, Bar, Histogram,
Scatter, Line), each paired with a domain-aware analysis engine. The
knowledge base maps 47 known column-name patterns
(e.g., \texttt{age}, \texttt{trtbps}, \texttt{chol}, \texttt{glucose})
to structured insight objects containing a human-readable label, a
semantic description, and a data-driven insight function conditioned
on column statistics. When a column name matches a knowledge-base
entry, the analysis panel generates domain-specific interpretations;
otherwise, general statistical language is produced.

\subsection{Layer 5 — Hybrid Runtime Repair Engine}

When a code cell raises a Python exception, the repair subsystem
receives the traceback, the current cell source, and the CSV column
schema. Algorithm~\ref{alg:repair} describes the resolution procedure.
The rule index contains 31 patterns across five error classes. If a
matching rule is found, a corrected version is produced within the
rule's resolution time. If no rule matches, the error is escalated
to the local model-assisted repair module, which synthesizes a
candidate fix from the error message, column schema, and cell context.
The repair is presented as a suggestion with explicit diff display;
the user must accept before the fix is applied.

\begin{algorithm}[t]
\caption{HybridRepair: Priority-Rule with Model Fallback}
\label{alg:repair}
\begin{algorithmic}[1]
\Require Traceback $T$, cell source $C$, CSV schema $S$
\Ensure  Corrected source $C'$, or \textsc{Unresolved}
\State Parse $T$ $\Rightarrow$ (\textit{errClass}, \textit{errMsg}, \textit{lineNo})
\ForAll{rule $r$ in \textsc{RuleIndex} (sorted by priority)}
  \If{$r$.\textsc{Matches}(\textit{errClass}, \textit{errMsg})}
    \State $C' \gets r$.\textsc{Apply}($C$, $S$)
    \If{\textsc{Verify}($C'$, \textit{expectedHash})}
      \State \Return $C'$
    \EndIf
  \EndIf
\EndFor
\State $\mathit{ctx} \gets$ \textsc{BuildContext}($T$, $C$, $S$)
\State $C' \gets$ \textsc{LocalModelModule.Infer}($\mathit{ctx}$)
\If{\textsc{Verify}($C'$, \textit{expectedHash})}
  \State \Return $C'$
\EndIf
\State \Return \textsc{Unresolved}
\end{algorithmic}
\end{algorithm}

evaluation, grouped into three size tiers of five datasets each:

\subsection{Manual Baseline Protocol}

Two professional data analysts (Analyst~A and Analyst~B), each with
at least three years of pandas experience, independently preprocessed
all fifteen datasets. Both were provided identical task specifications:
normalize all headers to lowercase underscore convention, remove exact
duplicate rows, identify null columns, and produce a cleaned CSV file
and typed-column summary. Total elapsed time was measured from first
file open to final export using a stopwatch application. Analysts
chose their own tools (pandas, Excel, OpenRefine) and worked without
time pressure. The reported manual baseline time per dataset is the
arithmetic mean of Analyst~A and Analyst~B's times.

Inter-analyst time agreement, measured as
$1 - |t_A - t_B| / \max(t_A, t_B)$, averaged 0.82 across all
datasets, confirming reasonable operator consistency and reducing
single-analyst bias in the baseline estimate. The same fifteen
datasets were subsequently processed through DataMentor's pipeline;
execution time was measured with \texttt{performance.now()} calls
bracketing the preprocessing sequence.

\subsection{Repair Benchmark: DRB-100}

To evaluate the runtime repair subsystem, we constructed the
\textbf{DataMentor Repair Benchmark (DRB-100)}, comprising 100 Python
notebook cell scripts derived from DataMentor's 13 auto-generated
analysis cells, each containing exactly one injected fault. The five
error categories reflect the distribution of errors observed in a
manual audit of 312 notebook sessions sampled from Kaggle dataset
discussion forums~\cite{kaggle2023}:

\begin{itemize}
  \item \textbf{E1\,---\,ImportError} (22 cases): missing or
        misspelled module imports.
  \item \textbf{E2\,---\,NameError} (18 cases): references to
        undefined variables caused by out-of-order cell execution
        or identifier typos.
  \item \textbf{E3\,---\,TypeError} (21 cases): type mismatch in
        function arguments, including passing string columns to
        numeric-only functions.
  \item \textbf{E4\,---\,AttributeError} (19 cases): access to
        absent DataFrame attributes, typically from schema-assumption
        violations.
  \item \textbf{E5\,---\,RuntimeError/Logic} (20 cases): semantically
        incorrect code that executes without exception but produces
        an incorrect or empty visualization.
\end{itemize}

Each benchmark item contains: (1) the original correct cell source;
(2) the injected faulty cell source; (3) the expected standard output
or the SHA-256 hash of the expected base64-encoded plot; and (4) a
difficulty label (\emph{Easy}, \emph{Medium}, \emph{Hard}) assigned
by two independent annotators reflecting traceback ambiguity and the
specificity of context required for repair. Inter-annotator agreement
on difficulty labels, measured with Cohen's $\kappa$, was 0.74,
indicating substantial agreement~\cite{landis1977}. The 14 items
(14\,\%) where annotators disagreed were resolved by a third annotator
acting as tiebreaker. Table~\ref{tab:drb100} shows the breakdown.

\subsection{Fairness and Evaluation Protocol}

Three methodological safeguards ensure evaluation fairness:

\begin{enumerate}
  \item \textbf{Temporal separation}: Benchmark items were constructed
        from cell templates that were not modified after the repair
        rule index was frozen. No benchmark item was used during rule
        authoring.
  \item \textbf{Single-pass constraint}: The repair engine was
        permitted exactly one repair attempt per benchmark item.
        No retry or iterative refinement was allowed, making the
        measured resolution rate a conservative lower bound on
        interactive utility.
  \item \textbf{Automated verification}: Resolution was determined
        by comparing the repaired cell's output hash against the
        expected output hash stored in DRB-100. Manual inspection
        was used only for E5 (logic) items where output variation
        is inherent to the visualization type.
\end{enumerate}

Repair latency was measured as the wall-clock time from traceback
receipt to candidate-fix generation, exclusive of user interaction time.

The 91.6\,\% overall reduction is driven by the elimination of
cognitive discovery overhead. Manual analysts must \emph{locate}
defects before correcting them, scaling linearly with schema width
and non-linearly with row count due to scanning behavior. DataMentor's
pipeline applies transformations unconditionally in a single pass,
removing discovery cost entirely. Browser-side execution overhead
(TypeScript parsing, React state updates) adds a fixed latency of
approximately 0.4~s, explaining the non-zero DataMentor times even
for small datasets. Pure pipeline execution time, measured in isolation
with \texttt{performance.now()}, is below 2~s for all datasets tested.

The residual DataMentor interaction time (2.1~min for small datasets)
reflects user-facing steps: uploading the file, reviewing the cleaning
summary table, and confirming the column-type classification. These
steps are user-controlled and could be further reduced by skipping
the confirmation step in future releases.

\subsection{Runtime Repair Resolution}

Table~\ref{tab:repair} and Fig.\,\ref{fig:repair} present DRB-100
resolution outcomes. The rule index achieves 100\,\% resolution on
E1 (ImportError) because every ImportError traceback contains the
missing module name as an explicit string, enabling exact-string
lookup in the rule index. The 88.9\,\% resolution on E2 (NameError)
reflects two items where the undefined identifier was introduced by
user-written cell code outside the generated template scope, giving
the rule index insufficient contextual information for a safe fix.

The 50.0\,\% resolution on E5 (RuntimeError/Logic) reflects the
fundamental difficulty of semantic repair: logic errors produce no
exception, and detecting an incorrect visualization output requires
understanding the expected result, which is inherently ambiguous
without a pre-computed reference hash. The overall 82\,\%
single-pass rate is conservative by design: the single-pass
constraint prohibits the iterative refinement that characterizes
interactive debugging sessions.

\subsection{Repair Latency}

Rule-based repairs achieve a mean latency of 0.8\,s
(SD\,=\,0.6\,s; range: 0.1--2.3\,s). Model-assisted repairs
produce a mean latency of 6.4\,s (SD\,=\,3.1\,s;
range: 2.1--14.7\,s). Manual debugging of equivalent errors,
measured as the time from error display to corrected cell
submission for the two analyst volunteers, had a median of
18.2\,min (IQR: 11.4--29.7\,min, equivalent to
1{,}092\,s). Even the slowest model-assisted repair (14.7\,s)
is more than $74\times$ faster than the median manual debugging
time. The speedup values are computed directly from these
measurements: $1{,}092 / 0.8 \approx 1{,}365\times$ for rule-based
and $1{,}092 / 6.4 \approx 171\times$ for model-assisted. These
ratios are bounded by the analyst sample ($n=2$) and should be
interpreted as indicative rather than definitive.

\subsection{Reproducibility}

All fifteen datasets were processed through DataMentor's pipeline
three times each, and the three output CSV files per dataset were
compared using SHA-256 hashing. All 15\,$\times$\,3 output files
produced identical hashes for identical inputs, confirming
full deterministic reproducibility across repeated executions.

The same triple-rerun procedure applied to the manual preprocessing
outputs yielded byte-level agreement in only 11.8\,\% of cases
(18 of 45 triple-pairs), since analysts made different ordering
choices when removing duplicate rows from datasets containing
value-identical clusters. Row-count agreement (ignoring column
ordering) was observed in 78.3\,\% of cases.

\section{Discussion}
\label{sec:discussion}

\subsection{Interpretation of Findings}

The 91.6\,\% preprocessing-time reduction is attributable to the
elimination of cognitive discovery overhead. Analysts must locate
the nature and position of data defects before correcting them;
DataMentor's pipeline removes this discovery cost by applying
transformations unconditionally and reporting results as a structured
audit log. This suggests that the benefit is structural rather than
implementation-specific: any fixed-pipeline tool operating on the
same defect classes would yield comparable reductions, provided its
transformation ordering is carefully chosen to maximize defect
surface coverage.

The 82\,\% repair resolution rate should be interpreted as a
conservative lower bound on practical interactive utility. DRB-100
applies a single-pass constraint and evaluates resolution against a
fixed reference output. In practice, users review the suggested fix,
optionally modify it, and rerun the cell. Multi-turn resolution rates
--- not measured in this study --- are expected to exceed the
single-pass figure, particularly for E4 and E5 items where the
first suggestion provides sufficient context for manual completion.

The near-zero byte-level reproducibility of manual preprocessing
(11.8\,\%) may surprise practitioners. The primary source of
non-reproducibility is not error but \emph{choice}: analysts apply
different resolution strategies for value-identical duplicate clusters
that differ in whitespace or case. DataMentor eliminates this
variation by applying a canonical strategy defined once in the pipeline
source code, making the strategy auditable and modifiable by
authorized users.

\subsection{Limitations}

Three principal limitations apply to this study. First, the manual
baseline involves only two analysts; a larger pool would increase
robustness of the time estimates, though high inter-analyst agreement
(0.82) suggests the current sample is representative. Second, DRB-100
is derived from DataMentor's own generated cell templates, which may
underrepresent errors arising in user-authored code with novel
structure outside the template scope. Third, the Pyodide runtime
imposes a package-loading latency of 8--14\,s on first use due to
WebAssembly initialization; this one-time cost is excluded from
preprocessing time measurements but affects perceived first-run
responsiveness.

\subsection{Generalizability}

DataMentor's preprocessing pipeline is domain-agnostic: it operates
on any CSV file conforming to standard comma-delimited format with a
header row. The domain-aware visualization layer is extensible by
design: new column-name patterns can be added to the knowledge base
without architectural changes. The repair rule index can be extended
with new rule patterns; each addition increases coverage for the
targeted error class without affecting unrelated classes, preserving
the priority-ordered resolution guarantee of
Algorithm~\ref{alg:repair}.

% =============================================================
\section{Conclusion}
\label{sec:conclusion}

This paper presented DataMentor, a serverless, browser-first platform
integrating deterministic CSV preprocessing, browser-native CPython
notebook execution, domain-aware visualization across ten chart types,
and a hybrid rule-guided runtime repair subsystem. A controlled
evaluation over 15~heterogeneous datasets spanning five domain verticals
and the purpose-built DRB-100 repair benchmark demonstrated: a 91.6\,\%
reduction in mean preprocessing time relative to a two-analyst manual
baseline; an 82\,\% single-pass automatic repair resolution rate with
rule-based latency of 0.8\,s versus a manual debugging median of
18.2\,min; and 100\,\% byte-level deterministic reproducibility.
Comparative analysis confirms that no existing system combines all
four capabilities in a unified, installationless, offline-capable
platform.

Future work will extend DRB-100 with user-authored cell errors, conduct
a formal usability study with SME and academic participant groups,
evaluate multi-turn repair resolution rates, and investigate streaming
CSV support for files exceeding available browser memory.
